## 1. Контекст

Пришла первая заявка на автоматизацию и внедрение ИИ в магазин на маркетплейсе. Клиент
хочет заполнить бриф. Брифа нет. Нужна отдельная страница на webkoth.com: аккуратная форма
для обычного селлера, с интерактивом, которая в конце собирает предварительную карту
автоматизаций.

Бриф строится на трёх опорах.

1. **Стандарт AIAS** (`/Users/minas/projects/AIAS`): вердикт ставится шагу, а не процессу;
   восемь вопросов вердикта; формы F0–F5; три цвета для владельца (AIAS-01); шкала
   автономии A0–A5; лестница стадий; паспорт задачи на 15 минут.
2. **Наши проекты**: библиотека процессов AIAS (карточки 02, 03, 04, 05, 07, 08, 12, 15)
   и кейсы сайта (`app/data/cases`).
3. **Внешние фреймворки** (исследование 17.09.2026, раздел 15): что из них превращено
   в вопросы брифа и в логику карты.

Что на сайте уже есть и переиспользуется: движок вердикта `lib/standard/verdict.ts`
(таблица решений с тестами), реестр кейсов, обработчик заявок
`app/api/evolution/lead/route.ts` (лимит, zod, ловушка, согласие, Telegram),
`lib/landing/telegram.ts`, цели Метрики `lib/analytics/ym.ts`, UI-кит `components/ui`,
токены дизайна в `app/globals.css`.

**Результат:** страница `/brief`, которую селлер проходит за 15–20 минут и получает карту;
нам в Telegram приходят короткое сообщение и файл с полной картой и ответами.

## 2. Цели и не-цели

**Цели**

- Селлер без технических знаний доходит до конца: простые вопросы, варианты кнопками,
  «Не знаю» везде, сноски к терминам.
- Карта честная и повторяемая: одни и те же ответы дают одну и ту же карту; никаких
  обещаний сверх того, что следует из ответов.
- Карта показывает главную мысль стандарта: в одном процессе часть шагов делает
  программа, часть готовит ИИ, часть остаётся человеку.
- Мы получаем всё, чтобы подготовить созвон: ответы, вердикты по шагам, флаги,
  что уточнить, подходящую ступень.
- Видно, на каком шаге бросают бриф.

**Не-цели**

- ИИ в рантайме на странице. Личный кабинет, база данных, хранение на сервере.
- Правка брифа после отправки. Письмо селлеру. Английская версия. CRM.
- Ссылки на бриф с лендингов и индексация: после 2–3 заполненных брифов, отдельным решением.
- Цены в карте и в файле для нас.

## 5. Путь селлера

Шесть шагов. Вариант «не знаю» есть везде, где селлер может не знать ответ; его нет
у вопросов о себе самом (площадки, команда, цели, контакты). Поля со значком **?**
раскрывают сноску из глоссария (раздел 8.3).

### Шаг 0. Вход (30 секунд)

Экран до первого вопроса:

- Заголовок: что получите в конце — карту: что отдать программе, что ИИ, что оставить себе.
- Сколько займёт: 15–20 минут, можно закрыть и вернуться, ответы сохраняются в браузере.
- Ответы уходят нам только по кнопке в конце.
- «Не знаю» — нормальный ответ: такие места уточним на созвоне.
- Кнопка «Начать». Если в браузере есть незаконченный бриф — «Продолжить» и «Начать заново».

### Шаг 3. Где уходит время (2 минуты)

Карточки процессов из каталога (раздел 6), сгруппированные по пяти группам. Селлер
отмечает всё, что отнимает время. У каждой отмеченной карточки появляется шкала
«часов в неделю» из пяти делений: `<1 · 1–3 · 3–5 · 5–10 · 10+`
(значения для расчёта: 0,5 · 2 · 4 · 7,5 · 12). Отдельная карточка «Своё» со строкой.

Затем: «Выберите до трёх, что болит сильнее всего — по ним зададим несколько вопросов».
Если отмечено три или меньше, выбраны все отмеченные. Выбрать можно и «Своё».

## 6. Каталог процессов

Шестнадцать процессов в пяти группах плюс «Своё». Файл `app/data/brief/processes.ts`.

### 6.1 Модель записи

```ts
type StepColor = 'auto' | 'ai' | 'human' | 'skip'

type ChainStep =
  | { kind: 'fixed'; label: string; color: StepColor }   // цвет не зависит от ответов
  | { kind: 'dynamic'; label: string }                    // цвет даёт вердикт по ответам (раздел 7.1)
  | { kind: 'approval'; label: string }                   // показывается, только если dynamic-шаг стал 'ai'

type ProcessEntry = {
  id: ProcessId
  group: 'content' | 'buyers' | 'pricing' | 'warehouse' | 'money' | 'management'
  label: string                     // «Ответы на отзывы»
  example: string                   // строка под названием на карточке шага 3
  hints: Partial<Record<DeepQuestionId, string>>   // подсказки к вопросам шага 4
  facts: {
    sideEffect: 'read' | 'notify' | 'write'
    singleRun: boolean
    personalData: boolean
    moneyData: boolean              // зависит от себестоимости и учёта (раздел 7.1, правило данных)
  }
  chain: readonly ChainStep[]       // ровно один dynamic-шаг
  branches?: readonly { when: string; step: ChainStep }[]   // «Отзывы 1–3★ → сразу к вам»
  readyMade?: { kind: 'cabinet' | 'service'; text: string; toolsKey?: ToolKey; checked: string }
  library?: { label: string; href: string }[]
  cases: readonly CaseSlug[]        // только существующие кейсы; пусто — ссылки нет
}
```

Правила каталога:

- В каждой цепочке ровно один `dynamic`-шаг; `approval` стоит сразу после него.
- У процессов с `sideEffect: 'write'` шаг `approval` обязателен. У `read` и `notify`
  его нет: сам dynamic-шаг только читает или сообщает, а действия с деньгами вынесены
  в отдельные шаги **Ч** (например, «Менять ставки»).
- Ссылки на кейсы только из реестра; кейса нет — ссылки нет. Выдумывать соответствие нельзя.
- `readyMade.checked` хранит месяц проверки (`2026-09`). Площадки меняют функции; строка
  старше шести месяцев подсвечивается тестом данных как требующая перепроверки.
- Подсказки `hints` пишутся на языке процесса, по образцу `app/data/landings/presets.ts`.

## 7. Правила: от ответов к карте

Все правила — чистые функции в `lib/brief/`. Движок `decideVerdict` не меняется.

### 7.1 Ответы процесса → вход вердикта (`to-quiz-input.ts`)

| Поле `QuizInput` | Откуда |
|---|---|
| `hasEtalon` | `etalon`: «да, несколько» или «есть 1–2» → `true`; «нет», «не знаю» → `false` |
| `dataReady` | `data`: кабинет, файл, таблица или учёт → `true`; «в голове», «не знаю» → `false`. **Правило данных:** если `facts.moneyData` и (`costKnown` = «нет» или `ledger` содержит только «в голове») → `false` |
| `useful` | `frequency` = «реже раза в неделю» и часы процесса < 1 → `'rare'`; иначе `'yes'`. `'no'` из брифа не выводится |
| `rule` | «инструкции на листке» → `'full'`; «придётся читать фото, письма» → `'freeInput'`; «без опыта не справится», «не знаю» → `'judgment'` |
| `check` | «видно сразу» → `'auto'`; «глазами за 10 секунд» → `'quick'`; «только я или опытный» → `'expert'`; не показан → `'expert'` |
| `singleRun` | `facts.singleRun` |
| `sideEffect` | `facts.sideEffect` |
| `irreversible` | `risk`: «увидят покупатели», «потеряем деньги», «штраф», «не знаю» → `true`; «ничего страшного» → `false`. Для `sideEffect` = `read` или `notify` всегда `false` (7.2 не даст шага «ИИ готовит» без шага утверждения в цепочке) |
| `personalData` | `facts.personalData` |

### 7.2 Вердикт → цвет dynamic-шага (`step-color.ts`)

| Вердикт | Цвет | Подпись для селлера | Примечание в карте |
|---|---|---|---|
| `f3` | auto | Программа, без ИИ | «Правило записывается полностью — это работа программы» |
| `f4` / `f5`, действие A4–A5 | auto | ИИ делает сам и сообщает | — |
| `f4` / `f5`, действие A2 | ai | ИИ готовит черновик | показывается шаг `approval` «Вы утверждаете» |
| `split` | ai | По этапам, с проверками | «Разобьём на этапы на созвоне» |
| `f1`, `f1f2` | human | Вы, ИИ-помощник подсказывает | — |
| `f0` | skip | Пока не трогать | «Редко и недолго — автоматизация не окупится» |
| `stopEtalon` | skip | Сначала образец | «Соберите 10–20 примеров „вот так правильно“» (текст из `hints.etalon`) |
| `stopData` | skip | Сначала порядок в данных | «ИИ поверх неточных цифр даёт уверенные ошибки» |

Дополнительно:

- `handover` = «оставить себе с помощником» и вердикт не `skip` → цвет human, подпись
  «Вы, ИИ-помощник подсказывает», примечание «Могла бы программа — оставили вам по вашему выбору»
  (только если вердикт был `f3`, `f4` или `f5`).
- Флаг `personalData` → примечание «В процессе данные покупателей: только российская модель или обезличивание».
- Флаг `rope` → примечание «Черновиков не больше, чем вы успеваете проверить».
- Цвет никогда не единственный сигнал: у шага всегда есть текстовая подпись.

### 7.3 Стадия магазина (`stage.ts`)

По `aiNow`, самооценка:

| `aiNow` | Для селлера | В файле для нас |
|---|---|---|
| не пользуемся | Стадия 0 · ИИ пока не пробовали | стадия 0 по лестнице AIAS |
| я сам в чате · сотрудники регулярно | Стадия 1 · ИИ пробуют в работе | стадия 1, стихийное использование |
| есть настроенные автоматизации | Стадия 1–2 · уточним на разборе | 1–2, по самоотчёту; уточняет аудит |
| пробовали своё, не пошло | Стадия 1 · есть опыт, который не взлетел | стадия 1 + флаг «застрявший пилот», текст из строки дословно |

Сноска к стадии пересказывает лестницу AIAS в трёх строках и ссылается на
`AIAS/guide/lestnica-stadiy.md` в публичном репозитории стандарта.

### 7.4 Часы и приоритет (`priority.ts`, коэффициенты в `coefficients.ts`)

Доля часов, которую возвращает dynamic-вердикт (**допущение, пересматриваем после первых брифов**):

| Вердикт | Доля |
|---|---|
| `f3` | 0,9 |
| `f4`/`f5` auto | 0,8 |
| `f4`/`f5` ai | 0,6 |
| `split` | 0,5 |
| `f1`, `f1f2`, «оставить себе» | 0,2 |
| `f0`, `stopEtalon`, `stopData` | 0 |

- **Часы процесса** = значение шкалы шага 3 × доля.
- **Итог карты** «≈ N ч/нед можно вернуть» = сумма по разобранным процессам, округление до целого;
  подпись «оценка по вашим ответам». Меньше 1 → «меньше часа в неделю: обсудим, стоит ли автоматизировать».
- **Приоритет** = часы процесса × пригодность; пригодность 0 при `skip`, 0,5 при `f5`
  и стадии 0 или 1 (агент не первым шагом, пока ИИ не освоен; стадия «1–2» сюда не входит),
  иначе 1.
- **«Начните с этого»** = процесс с наибольшим приоритетом > 0; при равенстве — порядок выбора в шаге 3.
  Если у всех 0 — блок «Начните с порядка» с первой причиной остановки
  (образец или данные) и тем, что подготовить.
- **Порядок в карте:** по приоритету по убыванию, затем процессы с `skip` с их «сначала…».

### 7.5 «Уже есть готовое»

- Показывается под процессом, если у записи есть `readyMade`.
- `kind: 'cabinet'` — «Уже есть в кабинете: …, попробуйте до любой разработки».
- `kind: 'service'` — «Есть готовые сервисы: …».
- Если в `tools` отмечен соответствующий `toolsKey` — «Вы уже пользуетесь: встроим, а не заменим».

### 7.6 Ступень для нас (`offer-step.ts`)

Первое сработавшее правило:

1. `aiNow` = «пробовали своё, не пошло» → **доведение пилота до production**.
2. `stopData` у двух и более разобранных процессов или `ledger` = только «в голове» → **аудит и карта**.
3. Есть «начните с этого» с цветом auto или ai и `implementer` ≠ «некому» → **первый процесс до production**.
4. Иначе → **разбор процесса, 30 минут**.

Цены не выводятся ни селлеру, ни нам: в карточке направления разбор стоит 50 тыс ₽,
на сайте бесплатен, расхождение не снято. Цену называет человек.

### 7.7 Флаги для нас (`flags.ts`)

- «Проверить категорию по правилу 1.6» — всегда, с категорией дословно. Названия
  и категории нанимателя в коде сайта не появляются.
- Персональные данные покупателей — список процессов.
- `ruOnly` = «да, обязательно».
- `implementer` = «некому».
- `access` = «нет».
- Застрявший пилот (7.3).
- Бюджет — как ответ.

### 7.8 Что уточнить на созвоне

Каждый ответ «не знаю» превращается в строку «уточнить: <вопрос> (<процесс>)».
Плюс `who` = «никто, руки не доходят» → «уточнить: нужен ли шаг вообще (В0)».

### 7.9 «Почему первым» и «что подготовить» (`explain.ts`)

Фразы фиксированные, выбираются условиями; не больше трёх на пункт.

**Почему первым** (только для «начните с этого»):

| Условие | Фраза |
|---|---|
| наибольшие часы среди разобранных | «больше всего часов в неделю» |
| `etalon` = «да, несколько» | «образцы у вас уже есть» |
| в цепочке показан шаг утверждения | «ошибку видно до того, как её увидят покупатели» |
| цвет dynamic-шага auto и вердикт `f3` | «без ИИ: программа, работает предсказуемо» |

**Что подготовить** (для любого пункта):

| Условие | Фраза |
|---|---|
| `stopEtalon` | текст из `hints.etalon` процесса |
| `etalon` = «есть 1–2» | «соберите ещё 10–20 примеров „вот так правильно“» |
| `stopData` из-за себестоимости | «посчитайте себестоимость каждого товара» |
| `stopData` из-за `data` | «сведите данные в одну таблицу или учёт» |
| показан шаг утверждения | «решите, кто утверждает и сколько минут в день у него есть» |
| `apiTokens` ≠ «да» и в цепочке есть шаг кабинета | «выпустить ключ доступа к кабинету — покажу как» |

## 8. Экран и карта

### 8.1 Экран брифа

- Прогресс-полоса сверху, строка «Шаг N из 6 · <название>», отметка «сохранено ✓».
- Слева — блок вопросов текущего шага. Ответы кнопками-чипами (`aria-pressed`), строки
  и текст — `components/ui/input`, `textarea`.
- Справа (≥ 1024 px) — **живой черновик карты**: `buildMap(частичные ответы)`. До шага 4
  выбранные процессы серые «ждёт подробностей»; после ответов пункт получает цвет и подпись.
  Итог часов пересчитывается на лету.
- На телефоне черновик свёрнут в нижнюю плашку «Карта: N пунктов ↑», открывается
  `components/ui/sheet`. Проверка на ширине 375 px без горизонтальной прокрутки.
- «Назад» на каждом шаге; обязательные поля подсвечиваются только при нажатии «Дальше».
- Стиль — токены сайта: JetBrains Mono, индиго, оранжевый акцент. Четыре цвета карты
  добавляются токенами в `app/globals.css` (`--brief-auto`, `--brief-ai` = `--primary`,
  `--brief-human`, `--brief-skip`) со своими значениями для тёмной темы.

### 8.2 Итоговая карта (вариант «план по порядку»)

Сверху вниз:

1. Надзаголовок «Предварительная карта · по вашим ответам», заголовок с площадками магазина.
2. Три показателя: «≈ N ч/нед можно вернуть · оценка», «N процессов разобрано», стадия со сноской.
3. Легенда четырёх цветов с подписями.
4. **«Начните с этого»** — выделенная карточка первого процесса: цепочка шагов в цветах,
   ветки, «почему первым» (из ответов: часы, образец есть, ошибку видно до публикации),
   «уже есть готовое», «что подготовить», «похожий проект →».
5. Остальные разобранные процессы в порядке приоритета, в том же виде, компактнее.
6. Строка «Не разбирали: <отмеченные без подробностей> · можно дополнить».
7. Кнопки «Скачать PDF» и «Начать новый бриф»; текст «Карта отправлена, свяжусь с вами»
   (или ошибка отправки, раздел 11).

«Похожий проект» ведёт на `/ru/cases/<slug>`; карточка библиотеки — на GitHub стандарта.

**PDF:** кнопка вызывает `window.print()`; стили `@media print` оставляют только карту,
разворачивают все процессы, убирают шапку, подвал и кнопки. Без библиотек.

### 8.3 Сноски

Файл `app/data/brief/glossary.ts`: термин → объяснение в 1–2 предложения простым языком
и, где нужно, пример. Сноска раскрывается по нажатию на **?** прямо под вопросом
(раскрывающийся блок, работает на касание и с клавиатуры; всплывающие подсказки по наведению
не используются).

Термины: артикул · FBO · FBS · DBS · API-токен (ключ доступа) · себестоимость ·
юнит-экономика · биддер · репрайсер · маркировка «Честный знак» · образец (эталон) ·
программа (без ИИ) · «ИИ готовит» · ИИ-агент · стадия.

## 9. Отправка и полная карта для нас

### 9.1 Поток

1. Селлер нажимает «Показать карту» на шаге 5.
2. Браузер отправляет `POST /api/brief` с ответами, `k`, `startedAtMs`, ловушкой `website`.
3. Сервер: лимит запросов → разбор JSON → потолок размера тела 64 КБ → zod (`lib/brief/schema.ts`)
   → ловушка (тихий 200) → время заполнения < 60 с от `startedAtMs` (тихий 200)
   → согласие обязательно.
4. Сервер **сам** строит карту `buildMap(answers)`, собирает сообщение и файл, отправляет в Telegram.
5. Ответ `{ ok: true }` или `{ ok: false, error }`. Карта у селлера открывается в любом случае,
   статус отправки показывается под ней.

### 9.2 Сообщение в Telegram (`render-telegram.ts`)

HTML, ≤ 1000 символов, пример:

```
Бриф: Анна · @anna_shop
WB + Ozon · 300–1000 артикулов · 10–100 заказов/день
Начать с: ответы на отзывы (≈ 3 ч/нед)
Ступень: первый процесс до production
⚠ категория: одежда и обувь — проверить по 1.6
метка: anna
```

### 9.3 Файл (`render-markdown.ts`)

Имя `brief-<метка или nolabel>-<ГГГГ-ММ-ДД-ЧЧММ>.md` (без транслитерации имени). Разделы:

1. Шапка: имя, контакт, дата, время заполнения в минутах, метка.
2. Флаги (7.7).
3. Магазин и стадия: ответы шагов 1–2, стадия с объяснением.
4. Разобранные процессы, для каждого: ответы дословно; `QuizInput`; вердикт, профиль
   автономии, флаги; цепочка шагов с формами и цветами; часы и приоритет с формулой;
   карточка библиотеки и кейсы.
5. Что уточнить на созвоне (7.8).
6. Отмеченные, но не разобранные процессы с часами.
7. Цели и рамки, свободный текст дословно.
8. Ступень (7.6).
9. Блок с исходными ответами, обрамлённый `~~~~json` / `~~~~` (не тройными кавычками:
   свободный текст селлера может содержать «```» и разорвать блок) — вход для
   `/task-verdict`, читающего этот блок под заголовком `## 8.` (14б).

### 9.4 Telegram: документ

В `lib/landing/telegram.ts` добавляется `sendTelegramDocument(filename, content, caption)`:
`multipart/form-data` на `sendDocument`, те же повторы и таймаут, тот же
`TELEGRAM_API_BASE_URL`. **Риск:** прокси (Cloudflare Worker) может не пропускать
multipart — проверить до реализации отправки. Запасной путь: если документ не ушёл,
отправить файл текстом несколькими сообщениями по ≤ 4000 символов с пометкой «документ не прошёл».

### 9.5 Дальше вручную (вне кода)

Файл пересылаем в Claude Code → `/task-verdict` даёт черновик к созвону → человек
проверяет → созвон. Адресат заносится строкой в `business-os/execution/contacts.jsonl`.

## 11. Ошибки и крайние случаи

| Ситуация | Поведение |
|---|---|
| Telegram не ответил | карта показана; под ней «Не отправилось. Нажмите „Отправить ещё раз“ или напишите в Telegram» с контактом из `lib/landing/contacts.ts`; ответы сохранены |
| Лимит запросов (429) | «Повторите через пару минут» (14б) |
| Ошибка валидации (400) | вернуть на шаг с первым неверным полем |
| localStorage недоступен | бриф работает, отметка «сохранено» заменяется на «не сохраняется в этом браузере» |
| Сохранён бриф старой версии | начать заново с пояснением «бриф обновился» |
| Не выбран ни один процесс на шаге 3 | «Дальше» недоступна, подсказка «отметьте хотя бы один» |
| Отмечен один процесс | шаг выбора «до трёх» пропускается |
| Все ответы «не знаю» по процессу | вердикт `stopEtalon`, карта честно говорит «сначала образец», список «уточнить» длинный |
| Документ не прошёл через прокси | запасной путь 9.4 |

- `priority`: формула, округление, равенство, «все нули» → «начните с порядка», агент при стадии ≤ 1.
- `offer-step`: четыре правила и их порядок.
- `build-map` на трёх эталонных магазинах (фикстуры):
  1. **Магазин из макета:** WB + Ozon, отзывы, остатки, реклама, сверка, поставки →
     «начните с» отзывов, остатки auto, сверка «сначала данные».
  2. **«Всё в голове»:** учёт в голове, себестоимость «нет» → денежные процессы `stopData`,
     ступень «аудит и карта».
  3. **Один владелец, редкие задачи:** «реже раза в неделю», <1 ч → почти всё `skip`/`f1`,
     итог «меньше часа».
- `build-map` на частичных ответах не падает (живой черновик).
- `explain`: каждое условие таблиц 7.9, не больше трёх фраз.
- Данные: уникальные id; ровно один dynamic-шаг в цепочке; `approval` только после dynamic
  и обязателен у `write`;
  подсказки к `etalon`, `rule`, `data` у каждого процесса; кейсы существуют в реестре;
  все упомянутые сноски есть в глоссарии; `readyMade.checked` не старше шести месяцев.
- `render-markdown`: снимок на фикстуре 1; блок JSON разбирается обратно в те же ответы.
- `render-telegram`: ≤ 1000 символов, HTML экранирован.
- Маршрут: ловушка, слишком быстрое заполнение, без согласия, слишком большое тело.
- Вручную: 375 px, тёмная тема, печать в PDF, прохождение от начала до Telegram на проде.

## 14б. Изменения по трём ревью кода (2026-09-17)

По результатам ревью ядра, серверной части и интерфейса (`fix-core-review.md`,
`fix-server-review.md`, `fix-ui-review.md`) в код внесены правки сверх того, что описано
выше. Часть изменений делает отдельные формулировки спеки выше устаревшими; такие места
исправлены прямо в тексте (раздел 9.3, раздел 11), здесь — сводка для дальнейшего чтения.

**Логика**

- F3 с флагом `irreversible` тоже получает шаг `approval`: по AIAS «исполняет код,
  утверждает человек», а не только F4/F5 с действием A2.
- `BriefMap` больше не хранит `offer`, `flags`, `clarify`: они вынесены в отдельный
  серверный `BriefInternal` (`lib/brief/internal.ts`), который в браузер не уходит.
- Флаг персональных данных считается по всем отмеченным процессам (`picked`), а не
  только по тем трём, что разобраны подробно.
- «Уточнить на созвоне» добавлен для ответа `who: 'service'` (уже делает сторонний сервис).
- В схему ответов добавлены инварианты: уникальные `picked[].id` и `deepChoice`,
  обязательная полнота `deepAnswers` для каждого разбираемого процесса, обязательный
  `customLabel` при выбранном «Своё».
- Редьюсер применяет значение поля, только если оно проходит проверку схемой этого поля;
  негодное значение состояние не меняет.
- Общая логика подробного разбора (`MAX_DEEP`, `needsCheck`, `isDeepComplete`, `deepList`)
  вынесена в отдельный `lib/brief/deep.ts`.
- Перед сборкой карты и файла сервер прогоняет ответы через `normalizeAnswers`: поля,
  скрытые обратной сменой ответа, в карту и файл не попадают.
- Ноль часов процесса показывается как «0 ч» с отдельной пояснительной пометкой, а не пустым местом.
- Заголовок итоговой карты — фиксированная строка, площадки магазина вынесены в отдельную строку «Площадки: …».

**Сервер и доставка**

- IP клиента для лимита запросов берётся через новый `lib/landing/client-ip.ts`
  (`X-Real-IP`, с защитой от подделанного `X-Forwarded-For`); используется в `/api/brief`
  и в `/api/evolution/lead`.
- Проверка времени заполнения больше не отбрасывает бриф, если часы устройства селлера спешат.
- Отброшенные брифы (ловушка, слишком быстрое заполнение) и ошибки валидации логируются
  на сервере без персональных данных.
- Свободный текст селлера в файле для нас (заметки, рассказ о неудачном пилоте) выводится
  построчной цитатой, чтобы не ломать заголовки и структуру файла.
- Блок с исходными ответами в файле обрамлён `~~~~json` / `~~~~` вместо тройных кавычек
  (раздел 9.3 ниже обновлён); `/task-verdict` читает этот блок под заголовком `## 8.`.
- Частичная доставка (сводка дошла, часть файла кусками не прошла) отвечает 200 и
  логируется отдельной строкой, а не считается провалом отправки.
- Между кусками текста файла в Telegram пауза 350 мс; пустые и состоящие из пробелов
  куски не отправляются.
- Текст ответа при лимите запросов (429) изменён на «Повторите через пару минут»
  (раздел 11 ниже обновлён).
- Клиент ждёт ответ сервера не дольше 30 секунд там, где браузер поддерживает
  `AbortSignal.timeout`; в старых браузерах запрос уходит без таймаута.

**Интерфейс**

- Страница брифа рендерится только в браузере через `next/dynamic` (`ssr: false`):
  без эффекта загрузки и мигания вводного экрана при чтении черновика.
- Черновик из localStorage читается ленивым инициализатором состояния, а не эффектом
  после первого рендера.
- Возврат на вводный экран не теряет уже введённые ответы: если бриф начат, «Продолжить»
  ведёт на текущий шаг, а не восстанавливает более старый сохранённый черновик.
- Первое неверное поле после «Дальше» или отправки прокручивается в видимую область и получает фокус.
- Заголовок каждого шага — фокусируемый `h1`, получает фокус при смене шага.
- Токены цвета текста шагов в светлой теме сделаны контрастнее.
- Печать карты из тёмной темы выходит в светлой палитре.
- Цели Метрики брифа не срабатывают повторно за одну загрузку страницы.
