# Кейсы на лендинге: карточки, карусели, страницы кейсов

Зафиксировано 23.08.2026. Основа: лендинг «Эволюция бизнеса» (`docs/2026-08-22-landing-evolyuciya-biznesa.md`
в каталоге `projects/docs`), закрытая заметка `business-os` со сводкой цифр по репозиториям
и документация рабочих проектов из закрытого каталога.

## Задача

На лендинге шесть блоков-постулатов, у каждого ровно одна плашка кейса
(`components/evolution/case-plaque.tsx`), и характеристики в ней инженерные: строки кода, коммиты,
модели БД, тестовые файлы. Бизнесу они ничего не говорят. Из четырёх десятков рабочих проектов
на странице представлены четыре.

Нужно: собрать кейсы из реальных проектов, перевести характеристики на язык бизнеса
(«болело → стало» и именованные характеристики вместо метрик кода), показывать несколько кейсов
в блоке каруселью, а по клику открывать отдельную страницу кейса со схемой, скриншотами
и ссылками на GitHub. Открытый код представлен наравне с коммерческим.

## Главное решение: кейс принадлежит не блоку, а набору углов

Одна prod-ready система приносит пользу больше чем по одному постулату. Финансовый контур
собрал все цифры в один источник (шаг 01), сделал видимыми деньги (шаг 02), сжал отчётность
с недель до получаса (шаг 05) и снял зависимость от найма, потому что его развивает сам
финансист (шаг 06). Привязка «один кейс — один блок» скрывает этот рычаг.

Поэтому единица данных — **система**, а единица показа — **угол**: пара «система + блок»
со своими «болело → стало» и своими характеристиками. У системы одна страница кейса,
на которой перечислены все её эффекты по постулатам.

Карточка системы, у которой углов больше одного, несёт пометку «та же система даёт эффект
ещё по N шагам». N вычисляется, а не пишется руками.

озера описываются внутри этого кейса и отдельным кейсом не выносятся.

цифры звучат внутри самих систем (73 % — товарный портал, 43 % — финансовый контур), и отдельная
карточка стала бы третьим повтором. Экспонат с тремя долями остаётся на лендинге.

**Запас на вторую волну:** платформа агентов (`agentic-os`), контент-фабрика (`content-factory`),

## Модель данных

Новый модуль `app/data/cases/`, отдельный от `app/data/evolution/`: кейсы больше не принадлежат
блокам, поэтому и данным блоков не принадлежат.

`registry.ts` — то, что не зависит от языка, единственный источник правды о структуре:

```ts
type CaseMeta = {
  kind: 'internal' | 'product' | 'oss'
  status: 'production' | 'pilot'
  blocks: readonly [BlockKey, ...BlockKey[]]   // порядок углов = порядок карточек
  links: { github?: string; npm?: string; site?: string }
  stack: readonly string[]                     // имена собственные, не переводятся
  screenshots: readonly { src: string }[]
}
```

`ru.ts` / `en.ts` — тексты. Угол самостоятелен:

```ts
type Chip = { icon: ChipIcon; label: string; value: string; note?: string }

type CaseAngle = {
  headline: string        // заголовок карточки именно в этом блоке
  pain: string            // болело, с точки зрения этого постулата
  outcome: string         // стало
  chips: Chip[]           // 2–3 пары «характеристика → значение»
  bar?: { filled: number; total: number; caption: string }
}

type CaseCopy = {
  title: string           // имя системы: страница кейса, крошки, пометка связи
  angles: Record<БлокиЭтойСистемы, CaseAngle>   // см. CasesCopy ниже
  detail: CaseDetail
}
```

Подписи типа и статуса не хранятся у каждой системы: они лежат по одному словарю на локаль
(`CASE_KIND_LABELS`, `CASE_STATUS_LABELS`) и выводятся из `meta`. Иначе три строки писались бы
заново у каждой из тринадцати систем на двух языках и разъезжались бы между локалями.

Набор углов проверяется компилятором, а не только тестом: `caseMeta` объявлен через
`as const satisfies`, а тексты типизированы отображением

```ts
type CasesCopy = {
  [S in CaseSlug]: Omit<CaseCopy, 'angles'> & {
    angles: Record<(typeof caseMeta)[S]['blocks'][number], CaseAngle>
  }
}
```

Лишний или забытый угол — ошибка компиляции в самой строке текста, а не падение теста
с сообщением. Остальные сквозные инварианты (структурное совпадение RU и EN, состав
`detail.effects`, запрет ссылок у клиентских систем) компилятор не видит — их держат тесты.

Шкала живёт в угле, а не в системе: 43 % относятся к шагу 06, в шаге 02 у той же системы доли нет.
Поле необязательное — где честной доли нет, секция не рисуется.

`ChipIcon` — закрытый словарь, иконка задаётся ключом, а не подбирается регуляркой по подписи,
как сейчас в `case-plaque.tsx:24`:

| ключ | иконка (lucide) | о чём |
|---|---|---|
| `scale` | `Boxes` | масштаб: «22 000 товаров», «48 инструментов» |
| `time` | `CalendarClock` | срок: «месяц», «один день до прода» |
| `people` | `Users` | кто ведёт: «финансовый аналитик», «оператор склада, без ИТ» |
| `replaced` | `Replace` | что заменили: «внешнюю PLM», «десять таблиц» |
| `money` | `Coins` | деньги: «3–8 млн ₽ рыночная альтернатива», «ДРР в плане ≤ 10 %» |
| `trust` | `ShieldCheck` | доверие: «сверка до единицы товара» |
| `auto` | `Zap` | автоматизм: «ежедневно, без рук» |
| `coverage` | `Layers` | охват: «4 двери наружу», «три площадки» |

`CaseDetail` — содержимое страницы:

```ts
type CaseDetail = {
  lead: string
  effects: { block: BlockKey; text: string }[]   // таблица эффектов по постулатам
  value: string[]                                // «что это даёт бизнесу»
  diagramNodes: string[]
  diagramNote: string
  beforeAfter?: { before: readonly string[]; after: string }   // вкладки «было / стало»
  how: string[]
  owner: string                                  // кто ведёт систему сейчас
  facts: { label: string; value: string }[]      // липкая панель, без «Тип» и «Статус»
  screenshots: { alt: string; caption: string }[]  // по индексу совпадает с registry
  metaTitle: string
  metaDescription: string
}
```

`index.ts` — выборки: `anglesForBlock(lang, block)`, `getCase(lang, slug)`, `casePath(lang, slug)`,
`isCaseSlug`. `casePath` — по образцу `homePath` / `cvPath` в `app/data/evolution/index.ts:20`.

`Record<CaseSlug, CaseCopy>` заставляет компилятор требовать обе локали для каждой системы.
Совпадение набора углов между локалями и с `registry.blocks` компилятор не проверит — это ловит тест.

## Компоненты

**`components/evolution/case-card.tsx`** заменяет `case-plaque.tsx` (файл удаляется).
Строение: шапка с бейджем «тип · статус» и заголовком-результатом → «болело / стало» знаками
✕ и ✓ без заливки, цвет только в знаке → пары «характеристика → значение» → необязательная тонкая
шкала с подписью → пометка связи, если углов больше одного → футер-ссылка по центру над
разделителем. Вся карточка кликабельна растянутой ссылкой на заголовке
(`after:absolute after:inset-0`); внешние ссылки получают `relative z-10`.
Механика `FactNote` (HoverCard «как считалось») переносится из `case-plaque.tsx:43` для чипов
с `note`.

**`components/evolution/case-carousel.tsx`** — одна карточка на всю ширину, автопрокрутка
каждые 7 секунд. Без новой зависимости: `flex snap-x snap-mandatory overflow-x-auto`
с `[scrollbar-width:none]` — тот же приём, что уже работает в `header-nav.tsx:160`.
Сверху счётчик «N из M» и стрелки, снизу точки.

Автопрокрутка останавливается: при наведении, при фокусе с клавиатуры внутри карусели,
после первого ручного переключения (насовсем), при уходе секции из вьюпорта и полностью
при `prefers-reduced-motion` (в проекте уже есть `animations/use-reduced-motion.ts`).
Все карточки остаются в DOM — страница индексируется и работает без JS.

**`components/evolution/block-section.tsx`** — вместо плашки карусель, добавляется проп `lang`.
Порядок в блоке: симптом → текст → анимация → экспонат (только 05 и 06) → карусель кейсов.

**Экспонаты.** Схема потока данных (блок 03) и вкладки «было руками / стало кнопкой» (блок 04)
переезжают на страницы своих кейсов — они описывают одну конкретную систему. Таблица запусков
(блок 05) и три доли 43/73/73 % (блок 06) остаются на лендинге, потому что говорят сразу
о нескольких системах, и поднимаются **над каруселью**, а не под неё: тогда блок читается как «тезис → анимация →
доказательство тезиса → конкретные системы», и не возникает вопроса, к какой карточке
карусели относится таблица.

## Страница кейса

Адрес `/[lang]/cases/[slug]` — тот же контур, что у CV. Выбран потому, что `buildPath`
в `components/language-toggle.tsx:15` уже корректно переключает язык на таком пути, и такой
маршрут в репозитории существовал до переезда 22.08 (`/[lang]/cases/hubmarket-stocksync`).
`generateStaticParams` — 13 систем × 2 языка = 26 страниц. Неизвестный slug или язык → `notFound()`.

Раскладка: контент слева, справа липкая панель. В панели — тип, статус, срок, кто ведёт,
что заменило, стек, ссылки GitHub / npm / сайт и кнопка заявки. Панель едет со скроллом,
поэтому «что это и куда нажать» видно на любой высоте; на мобильном она уезжает под заголовок
и перестаёт быть липкой.

Порядок секций слева: хлебная крошка «← слоган блока» → бейджи, H1, лид → «болело / стало»
→ **таблица эффектов по постулатам** → «что это даёт бизнесу» → схема → «было / стало» вкладками,
где есть → скриншоты → «как устроено» → другие кейсы этого шага → CTA → футер.

Таблица эффектов — то место, где виден рычаг: у финансового контура это четыре строки
«01 — собрал все цифры», «02 — видно деньги», «05 — отчёт за полчаса», «06 — развивает финансист».

Переиспользуется без переписывания: `LeadDialogProvider`, `HeaderNav` (добавляется необязательный
`anchorBase`, чтобы якоря шагов вели на главную; наблюдатель секций и так безопасно выходит,
когда секций нет — `header-nav.tsx:66`), разметка схемы из `DataFlowExhibit` (`exhibits.tsx:9`),
вкладки `BeforeAfterExhibit` (`exhibits.tsx:36`, обобщаются под данные кейса), сетка скриншотов
и чипы стека из `hubmarket-case.tsx`.

JSON-LD кейса — `components/cases/json-ld-case.tsx` по образцу `json-ld.tsx`.
Метаданные — `buildCaseMetadata(lang, slug)` в `lib/evolution/metadata.ts` по образцу
`buildHomeMetadata`: canonical на свой URL, hreflang ru/en/x-default=ru.

## Тексты и достоверность

Текст каждого угла пишется по документации проекта, а не по строке из README:

| Система | Источник фактуры |
|---|---|
| Финансовый контур | `README.md` и `docs/superpowers/` контура, маршруты `app/*` |
| Озеро данных | `docs/how-it-works.md`, `verification.md`, `analyst-guide.md`, `app-connection.md` озера |
| Учёт ИТ-хозяйства | `README.md`, `docs/ZABBIX-ROLLOUT.md` учёта, маршруты `app/(panel)/*` |
| Агенты рекламы | `CLAUDE.md` агентов рекламы |
| Магазин отвечает словами | `README.md`, `docs/QUICKSTART.md` (`mcp.hubmarket.ru`) |
| Стартовый шаблон | `README.md` (`webkoth/starter-template-app`) |
| Синхронизация остатков | `README.md` синхронизации остатков |
| Карта старой базы | `README.md` карты старой базы |
| Разбор финдокументов | `hubmarket-doc-parser/README.md` |
| База знаний площадок | `CLAUDE.md`, `PLAN.md` (`webkoth/rag-market`) |
| Деплой из чата | `README.md` пакета `@webkoth/mcp-timeweb` и плагина `webkoth/claude-code-plugins` |
| Рабочее место селлера | `README.md` (`webkoth/sellerai`) |
| Товарный портал | закрытая заметка `business-os` со сводкой по репозиториям (репозитория локально нет) |

Три уровня достоверности не смешиваются — это прямое требование `business-os`
(бизнес-эффект из git не извлекается, его подтверждает собственник):

- **Факт из репозитория** — 73 % и 43 % изменений, ~22 000 товаров, семь приложений за месяц,
  три выхода в прод в день первого коммита, сверка с площадкой до единицы товара и до копейки.
  Идут как есть.
- **Рыночная оценка** — «3–8 млн ₽ и 7–13 недель за сопоставимый модуль». Подаётся как ориентир
  по публичным оценкам подрядчиков, а не как наша цена.
- **Со слов владельца** — «отчёт за полчаса вместо недель», «без расширения команды»,
  «селлер работает без найма аналитика». В репозиториях этих цифр нет. До публикации они нужны
  от владельца в подтверждённом виде: было столько-то, стало столько-то. До подтверждения угол
  либо не публикуется, либо переформулируется без числа.

`ДРР ≤ 10 %` в `CLAUDE.md` агентов рекламы — **план**, а не достигнутый результат. На карточке пишется
«план ≤ 10 %»: иначе получается обещание, которого фактура не держит.

Обезличивание сохраняется: ни имени клиента, ни имён сотрудников, ни оборотов, ни ссылок
на приватные репозитории. Роли — «финансовый аналитик», «специалист по товару», «контент-менеджер»,
«оператор склада».

`app/data/cases/cases.test.ts` (vitest настроен, `vitest.config.ts`):

- каждая система описана в RU и EN;
- набор углов в обеих локалях совпадает с `registry.blocks` — единственная защита
  от расхождения языков;
- в каждом угле 2–3 чипа; `bar.filled ≤ bar.total`;
- у `kind: 'oss'` заполнена хотя бы одна ссылка;
- подписей скриншотов столько же, сколько файлов в реестре;
- в каждом блоке 3–4 угла — иначе автопрокрутка либо бессмысленна, либо растягивает блок
  на минуту;
- `detail.effects` перечисляет ровно те блоки, что в `registry.blocks`.

## Порядок работы

1. Данные и тесты: `types.ts` → `registry.ts` → `ru.ts` по документации проектов → `en.ts` → тесты.
2. Карточка и карусель.
3. Врезка в блоки, перенос экспонатов, удаление `case-plaque.tsx`.
4. Страница кейса: компоновка → маршрут → метаданные → JSON-LD.
5. Хвосты: `llms-markdown.ts`, `sitemap.ts`, редирект, README.
